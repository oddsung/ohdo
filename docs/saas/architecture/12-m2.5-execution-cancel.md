# 12. M2.5 — `execution.cancel` + REST trigger + mid-step subprocess 종료

- **상태**: 구현 착수 (2026-04-23)
- **이전 단계**: [11-m2.4-execution-log.md](11-m2.4-execution-log.md) — 로그 스트리밍
- **다음 단계**: M2.6 — S3/R2 pre-signed URL + 스크린샷 업로드

## 목표

M2.3 에서 queued → accepted → running → completed|failed 가 작동했다. M2.5 는 **사용자가 실행 중인 execution 을 중간에 끊을 수 있게** 만든다.

M2.5 완료 조건:

- `POST /v0/executions/{execution_id}/cancel` (Bearer agent) — user_id 스코프 권한 검증 후 WS 로 `execution.cancel` 프레임 push.
- 서버는 row status 를 여기서 바꾸지 않음. **에이전트가 `execution.result(status='cancelled')` 를 보내야 확정**.
- 에이전트가 `execution.cancel` 수신 시 현재 실행 중인 `WorkflowEngine.stop()` + `CodeSandbox.stop()` 호출 → 서브프로세스 즉시 terminate → 루프 break → `execution.result(status=cancelled)` 송신.
- 에러 택소노미: terminal 은 409, 오프라인 에이전트 503, 다른 user 404.
- 로컬 e2e + Railway wss e2e + 코어 회귀 25/25.

## API 스펙

### `POST /v0/executions/{execution_id}/cancel`

**인증**: Bearer agent token (M2.2 와 동일 dependency).

**권한**: `execution.user_id == agent.user_id` (다른 user 소유면 404).

**상태 게이트**: `execution.status` 가 `completed|failed|cancelled` 이면 409.

**에이전트 연결**: `registry.get(execution.agent_id)` 가 None 이면 503 (에이전트가 WS 에 안 붙어있음).

**응답**:

| 상태 | body |
|---|---|
| 202 | `{"execution_id": "...", "accepted": true}` |
| 404 | `{"detail": {"error": "execution_not_found"}}` |
| 409 | `{"detail": {"error": "already_terminal", "status": "completed"}}` |
| 503 | `{"detail": {"error": "agent_offline"}}` |

**동작**:

1. execution 조회 + user_id 검증.
2. 상태 게이트 + 오프라인 체크.
3. `execution.cancel` 프레임 빌드 + `ws.send_json`. 실패 시 503 로 변환.
4. row 는 그대로 둠. 어떤 컬럼도 변경하지 않음.
5. 202 반환.

## 에이전트 구현

### `ExecutionRunner` 확장

- `_active_engines: dict[str, WorkflowEngine]` 추가 (threading.Lock 으로 보호).
- `_cancelled: set[str]` — cancel 요청 받은 execution_id.
- `handle_frame` 에 `execution.cancel` 분기 추가 → `handle_cancel(execution_id)`.

```python
def handle_cancel(self, execution_id: str) -> None:
    with self._active_lock:
        engine = self._active_engines.get(execution_id)
        self._cancelled.add(execution_id)
    if engine is None:
        logger.info("cancel requested for unknown execution: %s", execution_id)
        return
    try:
        engine.stop()
    except Exception:
        logger.exception("engine.stop raised")
    sandbox = getattr(engine, "sandbox", None)
    if sandbox is not None:
        try:
            sandbox.stop()
        except Exception:
            logger.exception("sandbox.stop raised")
```

### `_run_execution_inner` 수정

- engine 생성 직후 `self._active_engines[execution_id] = engine` (락 내).
- finally 에서 `self._active_engines.pop(execution_id, None)`.
- `asyncio.run(engine.execute_session(...))` 반환 후 cancel flag 확인:
  - `execution_id in self._cancelled` → `final_status = "cancelled"`, error_summary=None (cancel 은 정상 종료).
  - 아니면 기존 로직 (`failed_steps == 0` → completed vs failed).
- cancel flag 쓴 뒤 `self._cancelled.discard(execution_id)`.

### engine.sandbox.stop() 의 효과

`CodeSandbox.stop()` (core/workflow_engine.py:329):
```python
def stop(self):
    """현재 실행 중인 서브프로세스를 강제 종료합니다 (F9 단축키)."""
    proc = self._current_proc
    if proc is not None and proc.poll() is None:
        proc.kill()
```

이게 핵심. subprocess 가 `proc.wait()` 에서 돌아오면 `StepResult` 가 failed 로 반환되지만, `WorkflowEngine.execute_session` 의 루프는 다음 iteration 에서 `self.should_stop == True` 를 감지해 break. 최종 `report.failed_steps` 는 1 이 될 수 있지만 우리는 이걸 "cancelled" 로 덮어쓴다.

## 서버 구현

### `routers/executions.py`

```python
@router.post("/{execution_id}/cancel", status_code=202)
async def cancel_execution(
    execution_id: str,
    agent: Agent = Depends(current_agent),
    session: AsyncSession = Depends(get_session),
):
    # 1. 소유 검증 (user_id 스코프)
    stmt = select(Execution).where(
        Execution.execution_id == execution_id,
        Execution.user_id == agent.user_id,
    )
    execution = (await session.execute(stmt)).scalar_one_or_none()
    if execution is None:
        raise HTTPException(404, {"error": "execution_not_found"})

    # 2. terminal 게이트
    if execution.status in ("completed", "failed", "cancelled"):
        raise HTTPException(409, {"error": "already_terminal",
                                   "status": execution.status})

    # 3. 오프라인 체크
    ws = registry.get(execution.agent_id)
    if ws is None:
        raise HTTPException(503, {"error": "agent_offline"})

    # 4. 프레임 빌드 + 전송
    frame = {
        "v": 0, "type": "execution.cancel",
        "id": str(uuid.uuid4()), "ts": _now_iso(),
        "payload": {"execution_id": execution_id},
    }
    try:
        await ws.send_json(frame)
    except Exception as exc:
        logger.warning("failed to push execution.cancel: %s", exc)
        raise HTTPException(503, {"error": "agent_offline"})

    return {"execution_id": execution_id, "accepted": True}
```

## 검증

### 로컬 e2e

1. `import time; time.sleep(8); print('too late')` 스텝 실행.
2. 1초 뒤 POST /cancel → 202.
3. ~1초 더 기다림 → `status=cancelled`, `executed_steps=1` (중간 kill 된 스텝 포함), `error_summary=None`.
4. terminal 상태 cancel → 409.
5. 다른 user 로 cancel → 404.
6. 실행 없는 agent_id 로 cancel → 503 (ws.stop() 후 POST).
7. 동일 cancel 두 번 → 두 번째 409.

### Railway e2e

동일 플로우 wss.

### 코어 회귀

25/25.

## Core 수정

**없음**. `WorkflowEngine.stop()` 과 `CodeSandbox.stop()` 모두 이미 public 메서드. 에이전트 런너가 둘 다 호출할 뿐. ADR 0001 4조건 미발동.

## 범위 밖

- 일정 시간 내 agent 가 result 안 보낼 시 서버 타임아웃 → `cancelled` 강제 확정 (reliability 개선) — M2.6+ 고려
- 웹 UI 취소 버튼 (Phase 3)
- 부분 실행 중단 (한 스텝 전체는 계속, 다음 스텝부터 중단) — 현재 engine 의 stop 은 between-step check 지만 sandbox.stop 으로 즉시 mid-step 도 가능
