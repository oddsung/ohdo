# 04. M1.2 — Device Flow 엔드포인트 + 브라우저 승인 페이지

- **상태**: 구현 착수 (2026-04-23)
- **이전 단계**: [03-m1.1-postgres-auth-schema.md](03-m1.1-postgres-auth-schema.md)
- **다음 단계**: M1.3 — Agent 트레이에 "Sign In" 추가 + Device Flow 클라이언트

## 목표

Agent 가 설치만 되면 **사용자 토큰 복붙 없이** 브라우저만 한 번 열어 로그인할 수 있는 흐름을 서버 쪽에서 먼저 완성한다. GitHub CLI·Google TV 등에서 검증된 OAuth 2.0 Device Authorization Grant (RFC 8628) 의 간소화 버전.

M1.2 완료 조건:

- `POST /v0/agents/device_code` — 새 device_code + user_code 발급
- `POST /v0/agents/device_token` — Agent 가 폴링하는 엔드포인트, 승인 시 `agent_token` 반환
- `GET /link` — 사용자가 브라우저에서 열어 user_code 를 입력하는 HTML 페이지
- `POST /link/approve` — user_code + email 을 받아 해당 device_code 를 approved 로 마킹 + user/agent 레코드 생성
- `device_codes` 테이블 (마이그레이션 0002)
- Railway 와 로컬 SQLite 양쪽에서 흐름 동작 확인

M1.3 에서 Agent 쪽에 이 API 를 호출하는 클라이언트를 붙인다. M1.2 범위에선 **서버와 curl/브라우저만으로 흐름이 성립** 하면 완료.

## 왜 "이메일 입력 stub" 로 로그인하는가

현 시점 **"사용자 로그인"** (이메일+비번, OAuth 소셜로그인, 매직링크 등) 기능이 아직 없다. 두 옵션 비교:

| 옵션 | 범위 | 단점 |
|---|---|---|
| **A. 이메일만 입력 (stub self-service)** ✅ | /link 페이지에서 user_code + email → 해당 이메일 user 가 없으면 생성 + device_code approve | 이메일 소유 증명 없음. **M1 범위에서만** 허용되는 임시 흐름. |
| B. 매직링크까지 M1.2 에 포함 | 범위 +1 주. SMTP/SES 설정·템플릿·토큰 TTL | M1 의 "인증·DB·WS 일직선" 이라는 원래 의도에서 벗어남 |

**A 로 확정**. 이메일 소유 증명은 M2+ (또는 클로즈드 베타 직전) 에서 매직링크·OAuth 소셜로그인으로 덧붙인다. M1.2 의 /link 승인 엔드포인트는 **명시적으로 "stub"** 임을 응답·로그에 표기해 향후 보안 감사 시 발견되지 않을 위험을 낮춘다.

## 스키마 — `device_codes`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | `UUID` | PK, default `gen_random_uuid()` | 레코드 PK |
| `device_code` | `TEXT` | UNIQUE, NOT NULL | Agent 가 폴링에 사용할 opaque 토큰 (예: `dev_` + 32 바이트 base32) |
| `user_code` | `TEXT` | UNIQUE, NOT NULL | 사용자가 브라우저에 입력할 짧은 코드 (예: `ABCD-1234`, 8 자리, 혼동자 제외) |
| `status` | `TEXT` | NOT NULL, default `'pending'` | `pending` / `approved` / `expired` / `denied` |
| `user_id` | `UUID` | FK → `users.id` ON DELETE CASCADE, NULL | 승인되면 채워짐 |
| `agent_name` | `TEXT` | NULL | Agent 가 발급 요청 시 선택적으로 보낼 수 있는 사용자 지정 이름 |
| `hostname` | `TEXT` | NULL | Agent 의 hostname (발급 시 함께 기록, agents 생성 시 복사) |
| `platform` | `TEXT` | NULL | `win32` 등 |
| `agent_version` | `TEXT` | NULL | `0.0.1` 등 |
| `expires_at` | `TIMESTAMPTZ` | NOT NULL | 발급 후 15 분 default |
| `interval_seconds` | `INTEGER` | NOT NULL, default `5` | Agent 권장 폴링 간격 |
| `approved_at` | `TIMESTAMPTZ` | NULL | 승인된 시각 |
| `consumed_at` | `TIMESTAMPTZ` | NULL | `device_token` 교환 성공으로 토큰이 발급된 시각 — 이후 재사용 차단 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, default `now()` | 발급 시각 |

인덱스:

- `device_codes_device_code_idx` — 폴링 조회
- `device_codes_user_code_idx` — 브라우저 승인 조회
- `device_codes_status_idx` — 만료 스윕용 (옵션)

## 엔드포인트 설계

### `POST /v0/agents/device_code`

Agent 가 호출. 인증 불필요 (익명).

**요청**:
```json
{
  "agent_name": "사무실 데스크톱",   // 선택, Agent config 또는 hostname 기반
  "hostname": "NEODAVINCI-PC",
  "platform": "win32",
  "agent_version": "0.0.1"
}
```

**응답 200**:
```json
{
  "device_code": "dev_6f7a...",
  "user_code": "ABCD-1234",
  "verification_uri": "https://ohdo-production.up.railway.app/link",
  "verification_uri_complete": "https://ohdo-production.up.railway.app/link?code=ABCD-1234",
  "expires_in": 900,
  "interval": 5
}
```

`verification_uri_complete` 는 Agent 가 사용자에게 "이 URL 을 클릭하면 코드가 자동 입력됩니다" 처럼 쓸 수 있는 편의 URL. RFC 8628 §3.3.1 스펙.

### `POST /v0/agents/device_token`

Agent 가 주기적으로 호출. 인증 불필요 (device_code 자체가 pre-auth).

**요청**:
```json
{
  "device_code": "dev_6f7a..."
}
```

**응답 200 (승인됨)**:
```json
{
  "agent_token": "ag_8b2c...",
  "agent_id": "b5a2...-uuid",
  "user_id": "9a1f...-uuid"
}
```

토큰은 한 번만 반환. 서버는 `token_hash` 만 저장.

**응답 400** (RFC 8628 §3.5 error 표준 차용):

| 조건 | `error` | HTTP |
|---|---|---|
| 아직 승인 안 됨 | `authorization_pending` | 400 |
| 폴링이 너무 빠름 | `slow_down` | 400 |
| 만료됨 | `expired_token` | 400 |
| device_code 가 유효하지 않음 | `invalid_grant` | 400 |
| 사용자가 거부함 | `access_denied` | 400 |

(M1.2 에선 `slow_down` 구현 생략 — 단순히 `authorization_pending` 만. 남용 발생 시 M1.5 이후 보강.)

### `GET /link`

브라우저에서 사용자가 방문. 쿼리파라미터 `?code=ABCD-1234` 가 있으면 자동 입력.

HTML 폼:

```
┌───────────────────────────────────┐
│  ohdo 기기 연결                    │
│                                   │
│  기기에 표시된 코드:                │
│  [ ABCD-1234        ]            │
│                                   │
│  이메일:                           │
│  [ you@example.com  ]            │
│                                   │
│          [ 연결 ]                  │
└───────────────────────────────────┘
```

### `POST /link/approve`

폼 제출을 받는다. **M1.2 stub 흐름**:

1. `user_code` 로 device_codes 조회, `status=pending` 이고 만료되지 않았는지 확인.
2. `email` 로 users 조회, 없으면 생성.
3. `device_codes.user_id = user.id`, `status = 'approved'`, `approved_at = now()` 로 업데이트.
4. 성공 페이지 표시: "기기가 연결되었습니다. 이 창을 닫아도 됩니다."

이 엔드포인트가 **이메일 소유 증명 없이 user 를 생성/연결** 한다는 사실을 로그에 `WARN stub approval: email={email}` 로 찍어 M2 매직링크 도입 시 이관 포인트를 명확히 한다.

## 토큰·코드 생성 세부

- `device_code`: `secrets.token_urlsafe(32)` → `"dev_" + ...`
- `user_code`: 8 자리, 혼동 문자 제외 (`I`, `O`, `0`, `1` 제외), `-` 중간 삽입 → 예: `ABCD-E3FG`
- `agent_token`: `secrets.token_urlsafe(32)` → `"ag_" + ...`
- `token_hash`: SHA-256(hex). bcrypt/argon2 불필요 — agent_token 은 이미 고엔트로피 (192 bit+) 라 무차별 대입 내성 충분.

## 보안 고려

**M1.2 범위**:
- device_code 와 agent_token 둘 다 고엔트로피 랜덤. DB 에는 `token_hash` 만. 원문은 발급 응답 이후 서버에 잔존하지 않음.
- device_code 15 분 TTL. 승인 후 1 회 교환으로 `consumed_at` 세팅 → 재사용 차단.
- /link 는 rate limit 없음 (M1.2 stub). user_code 는 8 자리 → brute force 공간 약 32^8 ≈ 10^12, 15 분 TTL 내 현실적으로 불가능. M2 에서 rate limit + 실패 카운트로 보강.

**M1.2 범위 밖 (의도적 deferred)**:
- 이메일 소유 증명 (M2 매직링크)
- /link 제출 CSRF 토큰 (같은 오리진 단일 폼이라 M2 까지 보류)
- agent_token rotation·revoke 대시보드 (M3+)
