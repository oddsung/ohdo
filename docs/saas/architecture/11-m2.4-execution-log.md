# 11. M2.4 — `execution.log` 스트리밍 + `execution_logs` 테이블 + 노이즈 필터

- **상태**: 구현 착수 (2026-04-23)
- **이전 단계**: [10-m2.3-execution-lifecycle.md](10-m2.3-execution-lifecycle.md) — execution lifecycle
- **다음 단계**: M2.5 — `execution.cancel` → `WorkflowEngine.stop()`

## 목표

M2.3 에서 실행 진행·결과는 WS 로 올라오지만 **실행 중의 로그** (엔진 상태 메시지, 각 스텝의 stdout/stderr) 는 보이지 않았다. M2.4 에선 그 공백을 채운다.

M2.4 완료 조건:

- 새 테이블 `execution_logs` 가 로컬 SQLite + Railway Postgres 양쪽에 존재.
- 에이전트가 실행 중 발생한 엔진 메시지 + 스텝 완료 시 stdout/stderr 를 배치로 `execution.log` 프레임 전송.
- 서버가 `execution.log` 수신 시 `execution_logs` 에 append (agent_id 소유 검증).
- `GET /v0/executions/{execution_id}/logs` — user_id 스코프 조회.
- **stderr 노이즈 필터** — Windows Python 런치 잡음 (`Could not find platform independent libraries`, `Consider setting $PYTHONHOME`) 제거.
- M2.3 에서 어긋났던 `error_summary` 가 필터 후 첫 라인을 취하도록 수정.
- `python -m tests.test_runner --suite core` 25/25 유지.

## 테이블 설계 — `execution_logs`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | `Uuid` | PK | 내부 PK |
| `execution_id` | `Text` | FK/index | `executions.execution_id` 와 문자열 조인. |
| `seq` | `Integer` | not null | 한 execution 안에서 순서. 프레임 배치마다 agent 가 monotonic 증가 값으로 매김. DB 입장에선 created_at 외 정렬키. |
| `step_id` | `Integer` | nullable | 어느 스텝과 연관된 로그인지. engine 초기 메시지 등은 null. |
| `stream` | `Text` | not null, indexed | `stdout` / `stderr` / `engine` |
| `line` | `Text` | not null | 한 줄 (max 2000자 agent clamp) |
| `created_at` | `DateTime(tz)` | not null, server default now() | Mixin 없이 단독 (updated_at 불필요) |

### 인덱스

- `execution_logs_execution_id_idx` — `execution_id` 기반 조회가 hot path.
- `execution_logs_execution_id_seq_idx` — 복합 (`execution_id`, `seq`) — 정렬 + 페이지네이션 효율.
- `execution_logs_stream_idx` — filter by stream 시.

### FK 설계 고민

`executions.execution_id` 는 유니크 Text 지만 PK 가 아니므로 FK 대상으로 바로 쓰기엔 어색함. 옵션:
- (A) `executions.id` (Uuid PK) 를 FK 로 사용 → 조인 한 번 더 필요.
- (B) `execution_id` (Text) 자체를 소프트 조인. FK 없이.
- (C) `execution_id` 에 FK + `unique=True` 인덱스 이미 존재하므로 가능.

**결정**: (C) — execution_id 에 FK. unique index 가 있어 FK constraint 가능하고, 에이전트·서버가 이 문자열로만 접근하므로 JOIN 불필요.

## 프레임 스펙

### Agent → Server

#### `execution.log`

```json
{"v": 0, "type": "execution.log", "id": "...", "ts": "...",
 "payload": {
   "execution_id": "exec_...",
   "entries": [
     {"seq": 1, "stream": "engine", "step_id": null, "line": "스텝 #1 실행 시작..."},
     {"seq": 2, "stream": "engine", "step_id": null, "line": "스텝 #1 완료 (68ms)"},
     {"seq": 3, "stream": "stdout", "step_id": 1, "line": "hello"},
     {"seq": 4, "stream": "stderr", "step_id": 2, "line": "RuntimeError: boom"}
   ]
 }}
```

- `entries` 는 1개 이상. 빈 배치는 전송하지 않음.
- `seq` 는 execution 내부 monotonic. 재전송 없으므로 단순히 agent 의 local counter.
- `stream` 외 값은 서버가 프레임을 버리지 않고 해당 entry 만 스킵.

### 서버 처리

- row 조회 (`execution_id` + `agent_id==current agent.id`) → 실패 시 WARN + 무시.
- 유효한 entries 를 bulk insert (`session.add_all(...)`, `await session.commit()`).
- 터미널 상태 (`completed|failed|cancelled`) 이후 수신 시 **거부하지 않고 그냥 저장**. 엔진이 result 송신 후 잔여 flush 를 보낼 수 있기 때문 (지연 도착).

## 에이전트 — runner.py 확장

### 버퍼 + flush

```python
class _LogBuffer:
    def __init__(self):
        self._seq = 0
        self._entries: list[dict] = []

    def append(self, *, stream: str, step_id: int | None, line: str) -> None:
        line = line.rstrip("\r\n")[:LOG_LINE_MAX]
        if not line:
            return
        if stream == "stderr" and _is_noise(line):
            return
        self._seq += 1
        self._entries.append({
            "seq": self._seq, "stream": stream,
            "step_id": step_id, "line": line,
        })

    def drain(self) -> list[dict]:
        out = self._entries
        self._entries = []
        return out
```

### 엔진 on_log 훅

`execute_session(... on_log=engine_on_log ...)` 에서:
- 현재 실행 중 step_id 는 `on_step_start` 에서 갱신하여 공유 변수로 보관.
- engine_on_log 는 `_LogBuffer.append(stream="engine", step_id=current_step_id, line=msg)`.

### step 완료 시 flush

`on_step_complete(step_id, result)` 에서:
- `result.output` 과 `result.error` 를 줄 단위로 buffer 에 append (stdout/stderr).
- `execution.progress` 는 이전 그대로 송신.
- **flush**: buffer 비우고 하나의 `execution.log` 프레임 송신.

### 실행 종료 직전 flush

`_run_execution_inner` 말미, `execution.result` 송신 **직전** 잔여 버퍼가 있으면 flush.

## 서버 — ws.py

### `execution.log` 핸들러

```python
async def _handle_log(payload, execution_id, *, agent, session):
    execution = await _fetch_owned_execution(execution_id, agent=agent, session=session)
    if execution is None:
        return
    entries = payload.get("entries")
    if not isinstance(entries, list) or not entries:
        return

    rows = []
    for e in entries:
        if not isinstance(e, dict):
            continue
        stream = e.get("stream")
        line = e.get("line")
        if stream not in ("stdout", "stderr", "engine"):
            continue
        if not isinstance(line, str) or not line:
            continue
        rows.append(ExecutionLog(
            execution_id=execution_id,
            seq=e.get("seq") if isinstance(e.get("seq"), int) else 0,
            step_id=e.get("step_id") if isinstance(e.get("step_id"), int) else None,
            stream=stream,
            line=line[:LOG_LINE_MAX_SERVER],
        ))

    if rows:
        session.add_all(rows)
        await session.commit()
```

`LOG_LINE_MAX_SERVER = 4000` — 두 번째 방어선 (agent 는 2000 이지만 서버는 악성 payload 대비 약간 높은 hard-limit).

## 서버 — GET `/v0/executions/{execution_id}/logs`

- 인증: `current_agent` (Bearer)
- 권한: `execution.user_id == agent.user_id` (404 if mismatch, detail 조회와 동일 정책).
- 쿼리:
  - `limit` (default 500, max 2000)
  - `offset` (default 0)
  - `stream` (optional: stdout|stderr|engine)
  - `step_id` (optional: int ≥ 1)
- 정렬: `seq ASC, created_at ASC` (seq 가 동일 값이어도 안정적 정렬).
- 응답:
  ```json
  {
    "items": [
      {"seq": 1, "stream": "engine", "step_id": null, "line": "...", "created_at": "..."},
      ...
    ]
  }
  ```

## 검증

### 로컬 e2e

1. 실행: 스텝 2개 — step1 `print('line1')\nprint('line2')`, step2 `raise RuntimeError('boom-m24')`.
2. 최종 `status=failed`, `executed_steps=2`, `failed_steps=1`.
3. `GET .../logs` → 최소 다음이 존재:
   - `engine` stream 여러 줄 (스텝 시작/완료 메시지).
   - `stdout` stream 에 `line1`, `line2`.
   - `stderr` stream 에 `RuntimeError: boom-m24` (노이즈 필터 후 첫 줄).
4. `GET .../logs?stream=stderr` → 노이즈 라인 없음.
5. `error_summary` → `step 2: RuntimeError: boom-m24` (또는 Python 의 traceback 마지막 라인).
6. 다른 user 의 agent 토큰으로 `GET .../logs` → 404.
