# 09. M2.2 — REST `POST /v0/executions` + `GET /v0/executions/{execution_id}` + `GET /v0/executions`

- **상태**: 구현 착수 (2026-04-23)
- **이전 단계**: [08-m2.1-executions-schema.md](08-m2.1-executions-schema.md) — `executions` 테이블 + 마이그레이션 0003
- **다음 단계**: M2.3 — WS `execution.start` 송신 + 에이전트 실행 어댑터

## 목표

[M2.1 에서 추가한 `executions` 테이블](08-m2.1-executions-schema.md) 위에 **얇은 REST 세 개** 를 올린다. 이걸로:

- Agent 가 "이 세션을 실행하려 한다" 를 서버에 기록 (A 패턴 = agent self-enqueue).
- Agent / 같은 user_id 가 "내 실행 상태" 를 조회.
- Railway Postgres 에 실제 row 가 생기는 것을 e2e 로 확인 (M2.1 잔여 검증).

M2.2 완료 조건:

- `POST /v0/executions` — Bearer agent 인증, body 받아 row 생성, `execution_id` 와 함께 반환.
- `GET /v0/executions/{execution_id}` — 같은 `user_id` 소유 executions 모두 조회 가능 (다른 user_id 의 row 는 404).
- `GET /v0/executions` — 같은 `user_id` 의 executions 리스트 (최신순).
- WS / 상태전이 / 실제 실행은 범위 밖 (status 는 항상 `queued` 로 남음 at M2.2 end).
- 로컬 e2e + Railway e2e + 코어 회귀 25/25.

## 결정

### A 패턴 (Agent self-enqueue) 로 시작

M2 궁극의 그림은 "웹 UI 또는 CLI 가 서버에 지시 → WS 로 Agent 에 푸시" 이지만, 웹 UI 인증이 아직 없고 `current_user` dependency 도 만들지 않았다. M2.2 는 **Bearer agent token** 하나로만 접근 가능. 사용자 세션 인증은 웹 UI 붙을 때 (M2.5+ / Phase 3) 추가.

### `execution_id` 포맷

`exec_<uuid4.hex>` — 32자 hex. ULID (시간 정렬) 는 디펜던시 추가 필요하고 지금은 과잉. 필요해지면 마이그레이션 없이 새 포맷을 섞어서 발급해도 되도록 Text 컬럼 그대로 유지.

### GET 권한 범위 — user_id 기반

같은 `user_id` 의 모든 executions 조회 가능. 즉 한 사용자가 여러 기기 (여러 agents) 를 소유하면 한 기기에서 다른 기기의 실행도 조회 가능. 이유:

- 실제 제품에선 사용자가 대시보드에서 모든 기기의 실행을 보는 게 자연스러움.
- agent_id 스코핑은 너무 좁아서 M2.3 이후 UI 구현 시 재설계 부담.
- 악의적 agent 가 다른 user 의 실행을 못 보게 막는 건 `user_id` 필터로 이미 달성.

### 상태 전이 M2.2 에선 보류

모든 새 row 는 `status='queued'`. `accepted` 로 옮기는 것은 M2.3 에서 Agent 가 `execution.accepted` WS 프레임을 보낼 때. M2.2 는 **읽기/쓰기 뿐** 이며 status 는 immutable.

## API

### `POST /v0/executions`

**인증**: Bearer `ag_...` (current_agent)

**Request body** (`ExecutionCreate`):

```json
{
  "session_snapshot": { ... },   // 선택: Session JSON 전체 (없으면 서버가 null 저장)
  "from_step": 1,                // 선택, 1-based
  "to_step": null                // 선택. null = 끝까지
}
```

- `session_snapshot` 은 선택이지만 M2.3 이후엔 사실상 필수. M2.2 에서는 일단 없이도 만들게 허용 (빈 실행 row 만들어보기).
- `from_step` / `to_step` 은 `Integer | None`.
- 기타 필드는 절대 입력받지 않음 (서버 발급 only): `execution_id`, `status`, `agent_id`, `user_id`, 집계 컬럼, timestamps.

**Response 201** (`ExecutionRead`):

```json
{
  "execution_id": "exec_3c4...32hex",
  "status": "queued",
  "agent_id": "uuid",
  "user_id": "uuid",
  "from_step": 1,
  "to_step": null,
  "total_steps": null,
  "executed_steps": null,
  "successful_steps": null,
  "failed_steps": null,
  "total_time_ms": null,
  "error_summary": null,
  "started_at": null,
  "finished_at": null,
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601"
}
```

- `session_snapshot` 은 응답에서 **제외** (payload 크기·민감도 고려). 상세 조회용 별도 엔드포인트가 필요해지면 M2.3+ 에서 추가. 상태 체크용으론 불필요.

**에러**:

- 401 (dependency) — missing/malformed/invalid/revoked
- 422 — Pydantic 검증 실패 (예: `from_step` 이 음수·문자열)

### `GET /v0/executions/{execution_id}`

**인증**: Bearer `ag_...`

**Response 200**: `ExecutionRead`

**404** — `execution_id` 가 존재하지 않거나, 존재해도 `user_id` 가 현재 agent 와 다르면. 404 는 존재 여부 정보를 누설하지 않는 보안 관행.

### `GET /v0/executions`

**인증**: Bearer `ag_...`

**쿼리 파라미터**:

- `limit` (default 50, max 200)
- `offset` (default 0)
- `status` (optional: filter by `queued` | `accepted` | ... )

**Response 200**: `{ "items": [ExecutionRead, ...], "total": <count-for-page-scope-later> }` — M2.2 에서는 `total` 생략하고 `items` 만. 페이지네이션 커서 방식은 데이터 많아지면 M2.4+.

**정렬**: `created_at DESC` (최신 먼저).

## 구현

### `app/schemas/execution.py` (신규)

```python
class ExecutionCreate(BaseModel):
    session_snapshot: dict | None = None
    from_step: int | None = Field(default=None, ge=1)
    to_step: int | None = Field(default=None, ge=1)

class ExecutionRead(BaseModel):
    execution_id: str
    status: str
    agent_id: uuid.UUID
    user_id: uuid.UUID
    from_step: int | None
    to_step: int | None
    total_steps: int | None
    # ... 집계 컬럼 ...
    started_at: datetime | None
    finished_at: datetime | None
    created_at: datetime
    updated_at: datetime

class ExecutionListResponse(BaseModel):
    items: list[ExecutionRead]
```

`schemas/` 폴더는 새로 만든다 (현재 pydantic 모델들이 각 라우터에 인라인으로 있음 → 재사용 필요성 생긴 M2.2 에서 분리).

### `app/routers/executions.py` (신규)

- `POST /v0/executions` — uuid4.hex → `exec_<hex>` 로 id 발급 → row insert → commit → refresh → `ExecutionRead` 로 직렬화.
- `GET /v0/executions/{execution_id}` — where `execution_id==param AND user_id==agent.user_id` → 없으면 404.
- `GET /v0/executions` — where `user_id==agent.user_id` + optional `status` + order by created_at desc + limit/offset.

### `app/main.py`

`executions` 라우터 include.

### `agents.router` 와 경로 충돌 주의

`agents.router` 는 prefix `/v0/agents` — 충돌 없음.

## 검증

### 로컬 e2e

1. 에이전트 생성 + 토큰 발급 (device flow 또는 직접 insert).
2. `POST /v0/executions` (body 없음, body only from_step, body with session_snapshot) — 각각 201 + `exec_` id.
3. `GET /v0/executions/{id}` — 본인 agent 로 200, 다른 agent 의 id 로 404, 다른 user 의 agent 로 404.
4. `GET /v0/executions` — 자기 executions 만 (순서는 최신순).
5. 401 taxonomy (dependency 이미 검증됨이지만 1번은 재확인).
6. `status` 쿼리 필터 동작.

### Railway e2e

1. `git push` 후 헬스 + 신규 라우터 200 확인.
2. 실제 device flow 로 `ag_...` 받아 → `POST /v0/executions` → 201 → `GET {id}` → 200. **이로써 0003 row 가 Postgres 에 실제 생김이 증명**.
3. CHANGELOG 에 execution_id·row insert 시각 기록.
