# 10. M2.3 — WS `execution.start` / `.accepted` / `.progress` / `.result` + 첫 실제 실행

- **상태**: 구현 착수 (2026-04-23)
- **이전 단계**: [09-m2.2-executions-rest.md](09-m2.2-executions-rest.md) — REST CRUD
- **다음 단계**: M2.4 — `execution.log` 스트리밍 (stdout 라인 배치 전송)

## 목표

[프로토콜 v0](../protocols/AGENT_PROTOCOL.md) 의 실행 이벤트 구간을 처음으로 코드로 증명. M1.5 에서 핸드셰이크만 놓았던 WS 채널로 **실제 RPA 실행** 이 흐르도록 한다.

M2.3 완료 조건:

- 서버: WS `/v0/agent` 핸드셰이크 성공 시 `agent_id` 를 **연결 레지스트리** 에 등록.
- 서버: `POST /v0/executions` → row 생성 후, 레지스트리에 해당 `agent_id` 가 있으면 그 WS 로 `execution.start` 프레임 push. 없으면 `queued` 로 남김 (catchup 은 M2.4+).
- 에이전트: `execution.start` 수신 → 워커 스레드 spawn → `WorkflowEngine.execute_session` 호출 → 스텝 진행에 맞춰 `execution.accepted` / `.progress` / `.result` 를 같은 WS 로 송신.
- 서버: 수신한 `execution.*` 프레임으로 `executions` row 를 상태 전이 (`queued → accepted → running → completed | failed`). `agent_id` 불일치 시 거부.
- 기존 핸드셰이크 (M1.5) · REST (M2.2) 동작 보존.
- `python -m tests.test_runner --suite core` 25/25.

## 프레임 스펙

모두 [프로토콜 v0](../protocols/AGENT_PROTOCOL.md#3-websocket-메시지-포맷) 의 최상위 래퍼 `{v, type, id, ts, payload}` 사용.

### Server → Agent

#### `execution.start`

```json
{"v": 0, "type": "execution.start", "id": "...", "ts": "...",
 "payload": {
   "execution_id": "exec_<hex>",
   "session_snapshot": { "session_id": "...", "steps": [...] },
   "from_step": 1,        // 1-based, nullable
   "to_step": null         // 1-based (inclusive), nullable
 }}
```

### Agent → Server

#### `execution.accepted`

```json
{"v": 0, "type": "execution.accepted", "id": "...", "in_reply_to": "<start.id>", "ts": "...",
 "payload": {"execution_id": "exec_..."}}
```

서버 동작: `executions.status = 'accepted'`, `started_at = now()`.

#### `execution.progress`

```json
{"v": 0, "type": "execution.progress", "id": "...", "ts": "...",
 "payload": {
   "execution_id": "exec_...",
   "step_id": 1,
   "success": true,
   "duration_ms": 123,
   "executed_steps": 1,
   "successful_steps": 1,
   "failed_steps": 0
 }}
```

서버 동작: 첫 progress 수신 시 `status='running'` (accepted → running 전이). `executed_steps`/`successful_steps`/`failed_steps` 를 프레임 값으로 **덮어쓰기** (에이전트가 누적값 송신).

#### `execution.result`

```json
{"v": 0, "type": "execution.result", "id": "...", "ts": "...",
 "payload": {
   "execution_id": "exec_...",
   "status": "completed",      // completed | failed
   "total_steps": 3,
   "executed_steps": 3,
   "successful_steps": 2,
   "failed_steps": 1,
   "total_time_ms": 45678,
   "error_summary": "step 3: ElementNotFound: ..."   // nullable
 }}
```

서버 동작: `status` 를 payload 대로 (단 허용 값 check), `finished_at = now()`, 집계 컬럼 + `error_summary` 저장. `status` 가 허용 값이 아니면 프레임 무시 + WARN 로그.

## 상태 머신 (M2.3 에서 첫 강제)

```
queued ──execution.start pushed──►  (db 변화 없음)
       │
       └── agent offline ─────────►  queued 로 유지

accepted ← execution.accepted
  │
  └── started_at = now

running ← first execution.progress OR execution.result(direct)
  │
  └── counters updated

completed ← execution.result(status="completed")
failed    ← execution.result(status="failed")
              finished_at = now
```

### 보안

서버 프레임 처리 시 **반드시 `Execution.agent_id == current agent.id`** 확인. 악의 에이전트가 다른 실행을 조작하지 못하게. 불일치는 WARN 로그 + 프레임 무시 (강제 close 는 과잉).

### 중복 / out-of-order

- `execution.accepted` 를 여러 번 받으면 상태가 `queued` 일 때만 적용, 이미 `accepted|running|...` 이면 무시.
- `execution.progress` 는 이미 `completed|failed|cancelled` 면 무시.
- `execution.result` 가 이미 종결된 row 에 오면 무시.

## 구현

### 서버

#### `app/registry.py` [신규]

```python
import uuid
from fastapi import WebSocket

_connections: dict[uuid.UUID, WebSocket] = {}

def register(agent_id: uuid.UUID, ws: WebSocket) -> None: ...
def unregister(agent_id: uuid.UUID, ws: WebSocket) -> None: ...  # 같은 ws 일 때만 제거
def get(agent_id: uuid.UUID) -> WebSocket | None: ...
```

FastAPI 단일 프로세스·단일 이벤트 루프 가정. 다중 워커로 확장 시 Redis pub/sub 로 교체 예정 (Phase 3).

#### `app/routers/ws.py` [수정]

1. `agent.hello` 수신 + `last_seen_at` 갱신 **직후** `registry.register(agent.id, websocket)`.
2. 기존 `while True: receive_text` 루프 → `receive_json` 으로 변경. 프레임 파싱 + 라우팅.
3. 지원 `type`: `execution.accepted` / `execution.progress` / `execution.result` (그 외는 debug 로그만).
4. 각 핸들러는 execution row 조회 (`execution_id` + `agent_id==agent.id`), 상태 전이 규칙 적용 후 commit.
5. 연결 끊김·close·예외 시 `registry.unregister(agent.id, websocket)` (finally).

#### `app/routers/executions.py` [수정]

`create_execution` 끝부분에:

```python
ws = registry.get(agent.id)
if ws is not None:
    frame = make_frame("execution.start", {
        "execution_id": execution.execution_id,
        "session_snapshot": body.session_snapshot,
        "from_step": body.from_step,
        "to_step": body.to_step,
    })
    try:
        await ws.send_json(frame)
    except Exception:
        logger.warning("failed to push execution.start; agent may have disconnected")
```

성공·실패 모두 201 응답은 그대로 (row 는 이미 저장됨). 에이전트가 WS 수신 못하면 `queued` 상태로 유지.

### 에이전트

#### `agent/runner.py` [신규]

`ExecutionRunner` 클래스:

- `handle_frame(frame: dict)` — type 이 `execution.start` 면 워커 스레드 spawn. 그 외 무시.
- 워커 스레드는:
  1. `execution.accepted` 즉시 송신.
  2. dict → `SimpleNamespace` 변환 (`session_id`, `steps`).
  3. `from_step` / `to_step` 슬라이싱 (엔진의 `start_from` 은 0 으로 고정 — 슬라이스된 배열 기준).
  4. `WorkflowEngine(visual_feedback_enabled=False, screenshot_on_error=False)` 생성.
  5. `asyncio.run(engine.execute_session(session, start_from=0, on_step_complete=...))`.
  6. 각 `on_step_complete` 콜백에서 `execution.progress` 송신.
  7. 종료 후 `execution.result` 송신 (성공/실패 판정 = `failed_steps == 0`).
  8. 예외 시 `execution.result` 를 `status=failed` + `error_summary="runner exception: ..."` 로 송신.

중복 방지: `_running: set[str]` + lock. 같은 `execution_id` 가 이미 실행 중이면 무시.

Core import:

```python
try:
    from core.workflow_engine import WorkflowEngine
except ImportError:  # PyInstaller 번들 or agent/ 에서 직접 실행
    import sys
    from pathlib import Path
    sys.path.insert(0, str(Path(__file__).resolve().parent.parent))
    from core.workflow_engine import WorkflowEngine
```

#### `agent/ws_client.py` [수정]

- 생성자에 `frame_handler: Callable[[dict], None] | None` 추가.
- `_connect_once` 에서 `self._ws = ws` / finally `self._ws = None` (send_frame 용).
- `_receive_until_closed` 에서 JSON 파싱 시도. `frame_handler(frame)` 호출 (예외는 로그 후 다음 프레임 진행).
- 새 메서드 `send_frame(frame: dict) -> bool` — 스레드 안전 send, 미연결 시 False.
- `send_lock` 은 `websockets.sync` 가 내부적으로 처리하지만 명시적 lock 추가 (재입성 안전).

#### `agent/agent_main.py` [수정]

- `ExecutionRunner()` 인스턴스 생성.
- `WebSocketClient(frame_handler=runner.handle_frame)` 로 넘기기.
- `runner.set_sender(ws_client.send_frame)` 로 역방향 연결.

## 검증

### 로컬 e2e

테스트 스크립트 (Python) 가:

1. seed user + agent + token 직접 DB.
2. uvicorn 기동.
3. 실제 `WebSocketClient` + `ExecutionRunner` 를 **스크립트 내부** 에서 생성, 토큰 꽂아 서버 연결.
4. 간단한 session_snapshot (스텝 2개: `print('ok')`, `1/0` 고의 실패) 을 `POST /v0/executions`.
5. 1~3초 대기 후 `GET /v0/executions/{id}` → `status=failed`, `executed_steps=2`, `successful_steps=1`, `failed_steps=1`, `error_summary` 채워짐 확인.
6. 전체 happy path (모두 성공) 도 별도 실행으로 검증.
7. agent_id mismatch 시도: 다른 agent 의 WS 로 남의 execution_id 에 `execution.accepted` 보내 → 서버가 무시 + row 무변화 확인.

### Railway e2e

같은 플로우를 Railway 대상으로. ExecutionRunner 를 내 개발 PC 에서 구동하여 Railway WS 에 붙이고, 거기서 `POST /v0/executions`. 실행 결과가 Postgres 에 반영되는지 `GET` 으로 확인.
