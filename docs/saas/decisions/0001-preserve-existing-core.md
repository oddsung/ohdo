# ADR 0001: 기존 `core/`·`ui/`·`main.py` 는 **감싸는 것을 기본**으로 하되, 필요 시 수정 허용

- **상태**: Accepted (revised 2026-04-22)
- **최초 작성일**: 2026-04-22
- **개정일**: 2026-04-22 — "완전 수정 금지" → "wrap-first, 필요 시 수정 허용"
- **결정자**: @oddsung

## 개정 요약

최초 버전은 "기존 `core/`·`ui/`·`main.py` 를 **절대 수정하지 않는다**" 였다. 사용자의 의도가 "회귀 방지" 이지 "수정 전면 금지" 가 아님을 확인하고 다음과 같이 완화:

- **기본 방침**: wrap-first (신규 파일로 감싸는 것을 우선).
- **예외**: SaaS 연동을 위해 기존 파일 수정이 불가피하면 수정 허용.
- **조건**: 수정 전 사전 고지, 수정 후 회귀 테스트, CHANGELOG 기록, 수정 범위 최소화.

이하 본문은 개정 후 기준으로 다시 씀.

## 컨텍스트

ohdo.ai 는 현재 동작하는 PyQt6 데스크톱 RPA 앱이고, 사용자는 이것을 **SaaS 로 확장**하려고 한다. [ROADMAP.md Phase 1](../../ROADMAP.md) 은 원래 "`core/session_manager.py` 의 `Path("data/sessions/")` 하드코딩을 `SessionRepository` 인터페이스로 대체", "`ui/main_window.py` 를 1,649줄 → 600줄로 축소" 같은 **인플레이스 리팩토링**을 전제로 했다.

그러나:

1. SaaS 구현 자체가 이 프로젝트에서 처음이다. 백엔드·Agent·웹 UI·결제 어느 것도 아직 만들어 본 적 없다.
2. 데스크톱 앱은 이미 사용자가 쓰는 수준으로 돌아가고 있다. 대규모 리팩토링 중 회귀가 생기면 SaaS 작업을 멈추고 불끄러 가야 한다.
3. 동시에 **SaaS 와 연결하려면 기존 코드의 내부 동작에 개입해야 하는 순간**이 온다 (예: `WorkflowEngine` 이 실행 이벤트를 외부로 내보낼 수 있도록 콜백/이벤트 훅을 심는 것). 이걸 외부 facade 로만 흉내 내려 하면 코드가 기괴해진다.

## 결정

### 기본 — wrap-first

SaaS 확장 변경은 **가능한 한 신규 파일/디렉터리**에 한정한다:

- 새 모듈 추가 (예: `core/app_service.py`, `core/storage/`, `agent/`, `packages/backend/`, `packages/web/`).
- 기존 모듈을 import 해서 **감싸는** facade/wrapper 패턴.
- 상속보다 composition 우선 (기존 클래스가 바뀌어도 영향 최소화).

이유는 단순하다: 회귀 리스크 최소화 + "SaaS 레이어 전체 되돌리기" 가 쉬움.

### 예외 — 기존 파일 수정 허용 조건

다음 네 가지를 모두 만족하면 기존 `core/`·`ui/`·`main.py` 수정 가능:

1. **사유가 SaaS 연동에 직접 필요함**: "UI 코드가 지저분해서" 같은 부수적 이유로는 수정하지 않는다.
2. **사전 고지**: 수정 시작 전에 어떤 파일을 왜 수정하는지 사용자에게 한 번 알린다 (승인 대기까지는 필요 없지만 투명성 확보).
3. **회귀 테스트 그린**: 수정 후 반드시 `python -m tests.test_runner --suite core` 실행. 관련 있으면 `prompt_quality`, `ai_integration` 도. 실패하면 원복 또는 수정.
4. **CHANGELOG 기록**: [docs/saas/CHANGELOG.md](../CHANGELOG.md) 에 수정된 파일과 이유를 남긴다.

### 여전히 피할 것

- **목적 불분명한 대규모 리팩토링**: `ui/main_window.py` 를 600줄로 축소하는 등 Phase 1 에서 원래 계획된 리팩토링은 **SaaS 작업과 별도 브랜치**에서 진행한다. SaaS 작업 PR 에 섞지 않는다.
- **SaaS 와 무관한 "정리"**: 스타일 고침, 주석 보강 같은 건 별도 작업. 이 정책의 예외 조항이 아님.

## 결과

### 장점

- 기본적으로 회귀 리스크가 낮음 (신규 파일로 일하므로).
- 꼭 필요한 수정은 막지 않으므로 구현이 현실적.
- 조건 4가지(사유·고지·테스트·기록)가 자연스러운 품질 게이트 역할.

### 단점 및 대응

- "이게 정말 수정이 필요한 건가?" 판단이 매번 필요 → 어떤 경우가 예외인지 이 문서와 CHANGELOG 의 과거 사례를 보고 판단.
- 수정이 누적되면 원래 코드와 SaaS 연동 코드가 섞여 간다 → 분기별로 리팩토링 기회를 만들어 다시 레이어 정리.
